I added Storybook to my site. It was absolutely overkill for my personal corner of the internet, but it is also my playground for testing things. And test things I will!

I have to say I like it. It gives me a clear visual of my main components at a glance. I can see the benefit of using it if I were in a team that was onboarding new people and encouraging backend-inclined members to code on the frontend. It would also be useful for interns and graduate developers to figure out how props change the appearance of components.

For the well-defined components, I created a folder to house the main component, the styled component, and the Storybook file. For example:

```jsx
📁 Button
	📃 Button.stories.tsx
	📃 Button.styled.ts
	📃 Button.tsx
```

## Deployment

I originally wanted Storybook on its own subdomain, but I took the quicker route and served it at `/storybook` inside the main site deployment. That meant Storybook was rebuilt on every deploy, which slowed my builds down.

It now lives at [storybook.michaelsavage.ie](https://storybook.michaelsavage.ie). The site has since moved to Cloudflare Workers, and Storybook is deployed as its own small Worker that only serves the static build. A GitHub Action rebuilds and deploys it whenever I push changes to my atoms, molecules, or icons folders, so the main site build doesn't touch Storybook at all.

Before deploying, the action runs every story as a browser test using Storybook's Vitest addon, so a broken component doesn't make it onto the subdomain.

## Learning curve

Cursor did a lot of the heavy lifting here, even though the documentation is clear and concise. Time was definitely halved for the use case I wanted, and after the second and third story components, I started to see the pattern and I was able to adjust the styling to my needs.

It didn't take even half a day to get up and running. The Storybook setup command does a thorough job of getting you going with an example. All you need to run is:

```jsx
npm create storybook@latest
```

## Will I keep using it?

In a larger codebase that uses many components, yes absolutely. Not everything needs a story though, and I'd like a better understanding of which code this workshop isn't suited for. For example, it doesn't make sense to add it for very trivial wrappers, entire pages or routes, purely data-driven views, or Heads-up UI.

**Very trivial wrappers**  
	Components that do nothing more than wrap children to inject CSS or context, without any visible variation.

**Entire pages or routes**  
	Full-page layouts often depend on router context, global stores or data-fetching. They're harder to isolate and don't benefit as much from “knobs.”

**Purely data-driven views**  
	If a component just renders JSON or a simple table with no UI states to experiment with, it's low ROI.

**Heads-up UI (toasts, alerts)**  
	Leave them out unless you want to play with timing, positions and interactions.
